# ao-api-forge

Projects the upstream artifacts into the feature's HTTP contract and an async job contract.
Parallel to `sdlc:api-forge`, not a replacement: it keeps the same protocol (gate, scenario A/B,
rules bootstrap, derive, drift check, report on every run, `--reconcile`) and changes the defaults,
the inputs, the drift checklist and the codegen check (see "What differs from sdlc:api-forge").

The contract is **derived, never hand-written**: data-model and migrations give types and
constraints, the SAD §6 sequences give error branches and async actors, the PRD gives the endpoint
list, the ao-prd §5.1 catalogue gives every error code and §10 the 403s.

Shared mechanics are copied into `references/shared/` so the skill runs without the plugin:
[surfaces](./references/shared/surfaces.md) · [size](./references/shared/size-matrix.md) ·
[handoff](./references/shared/handoff.md) · [ask style](./references/shared/ask-style.md).

## Audience

The backend lead answers; the board chair is never asked about the contract. Questions in
Ukrainian, plain words, every term glossed once ([ask-style](./references/shared/ask-style.md));
every option says what the skill will write next.

## Inputs

- `<slug>`; `--reconcile` re-derives after an upstream artifact changed.
- **Gate (hard refuse):** `docs/features/<slug>/PRD.md` or `PRD.ao-prd.md`. Missing -> «run
  `/ao-prd <slug>` or `/sdlc:write-prd <slug>` first». Both present -> one `AskUserQuestion`: which
  PRD to derive from (the ao-prd one is recommended: it has §5.1 and §10).
- **SAD:** `sad.md` / `sad.ao-architecture.md` (same pick rule). Frontmatter `target_surfaces` picks
  the contract forms ([surfaces](./references/shared/surfaces.md)): `backend-service` -> OpenAPI
  delta, `worker` -> `events.md`, `web-frontend` consumes the contract (orval check only). §6
  sequences give error branches and async actors; §8 gives the error, auth and job rows.
- **Data model (decides the scenario):** `data-model.md` or `data-model.ao-data-model.md` plus
  the staged `docs/features/<slug>/migrations/*.sql`. Present -> scenario A; absent -> scenario B.
- **Repo (always read):** `services/core/api/openapi.yaml`, `services/core/migrations/*.sql` (columns of
  tables the feature reads), `services/core/internal/platform/httpapi/`, every
  `internal/*/adapters/http/gen/oapi-codegen.yaml`, `apps/web/orval.config.ts`,
  `services/core/tools/go.mod` (oapi-codegen version), `docs/adr/*.md`, `CLAUDE.md`. Then read
  [`./references/repo-practice.md`](./references/repo-practice.md) and reconcile it with what the
  repo says (the repo wins; the difference goes to the report).
- **Optional:** feature `adr/` (an ADR overrides a default and the report says "deviation by ADR-NNNN"),
  `CONTEXT.md` glossary (schema names in its English column), `.size` (absent -> M).

## Output and collision rule

- `docs/features/<slug>/contracts/openapi.yaml` from [`./templates/openapi.yaml`](./templates/openapi.yaml),
  `contracts/api-sync-report.md` from [`./templates/api-sync-report.md`](./templates/api-sync-report.md),
  `contracts/events.md` from [`./templates/events.md`](./templates/events.md) iff `worker` is a target
  surface or a §6 flow enqueues a job.
- If `contracts/` exists and its `api-sync-report.md` `**Generated by:**` line is not
  `ao-api-forge` (or there is no report), never touch it: write `contracts.ao-api-forge/` with the
  same three files. This is how the two skills are compared on one feature.
- First HTTP run only: `.claude/rules/openapi.md` from
  [`./templates/rules-openapi-baseline.md`](./templates/rules-openapi-baseline.md).

## Scenarios A vs B and `--reconcile`

Same semantics as the course skill, detail in [`./references/drift-check.md`](./references/drift-check.md):

- **A** (data-model present): every field has a `high` origin in a column; constraints follow the
  mapping in [repo-practice](./references/repo-practice.md#field-mapping-from-ddl); `unresolved_origins` empty.
  Only A can reach plain `PASS`.
- **B** (no data-model): fields inferred from PRD names, §6 messages and existing tables in
  `services/core/migrations/`; every inferred field goes to `unresolved_origins`; verdict at best
  `PASS (with deferrals)`.
- **`--reconcile`**: re-read inputs, switch B -> A, tighten types from the DDL, refresh confidence,
  surface every inferred field that now disagrees with the model (real drift), re-read the previous
  report's `Deferrals` and close or carry each. `info.version` is never bumped silently.

## Protocol

1. **Gate, picks, scenario.** Check the PRD gate; pick PRD / SAD / data-model variants (one
   `AskUserQuestion` per real choice). Read `target_surfaces`. Say "found / missing" for SAD,
   data-model, staged migrations and the scenario chosen. No HTTP surface -> skip to `events.md`
   (worker only) or stop with a one-line note.
2. **Rules bootstrap.** `.claude/rules/openapi.md` absent -> copy the baseline and tell the user «I
   wrote a baseline API rules file for this repo; edit it if the team disagrees». Present and
   written by `sdlc:api-forge` (its header comment) -> do not overwrite; one `AskUserQuestion`:
   replace with the ao baseline / keep and record every conflicting default as a deviation. Present
   otherwise -> read it; a team edit counts like an ADR.
3. **Copy the templates** to the collision-rule path. `info.description` from PRD §1.
   `info.x-merge-target: services/core/api/openapi.yaml`.
4. **Derive operations and schemas.** One or more operations per PRD §4 user story, each with one
   tag (its bounded context), a path under `/<context>/`, an `operationId` in lowerCamel
   verb-noun form unique across the merged contract. Request `New<Entity>` / command
   `<Verb><Entity>Request`, response `<Entity>`, list `<Entity>Page` - all in `components/schemas`,
   used through `$ref`. Field types and constraints per
   [field mapping](./references/repo-practice.md#field-mapping-from-ddl). A field with no origin in
   any input -> `AskUserQuestion` (where does it come from?), never invented. Lists use the repo's
   cursor parameters and page wrapper.
5. **Errors from §5.1, §6 and §10.** For each operation collect: every §6 `alt`/`else` branch, every
   §5.1 code whose AC the operation serves, the §10 refused actions (-> 403 or 409), and the auth
   pair 401/403 on every protected operation. Map kind -> status per
   [status mapping](./references/repo-practice.md#errors-and-status-mapping), reference the reusable
   responses, and list the codes per status in the operation's `x-problem-types` map. A response the
   contract needs but no §6 flow shows is a **sequence gap** (drift point 5).
6. **Auth, concurrency, async.** Global `security: [SessionCookie: []]`; public operations
   (`/system/health`, sign-in callbacks) declare `security: []`. Edits of a revisioned aggregate
   carry `revision` and answer 409 on a stale one. Every River job a §6 flow enqueues gets an
   `events.md` entry (ids only, unique key, retries, trace context).
7. **Examples.** Request, success and error example per operation; placeholder data only
   (`<name>@example.test`, «Тестовий Член Правління», `00000000-0000-7000-8000-000000000001`).
8. **Codegen check.** Run the scratch oapi-codegen + `go build` on the delta and the scratch orval
   run, per [`./references/codegen-check.md`](./references/codegen-check.md). A failure is drift
   point 9 (core).
9. **Drift check + report.** The 9-point checklist in
   [`./references/drift-check.md`](./references/drift-check.md): 1-3 forward (core), 4-5 back-feed
   (supporting), 6-9 repo points (core). A core ✗ or ≥3 open flags pauses the run; resolve each
   finding with `AskUserQuestion`: Accept as is / Fix the contract / Save as open question / Fix the
   source first. Derive the verdict, write the report on every run, FAIL included.
10. **Commit and handoff.** One commit with the contract folder (and the rules file if bootstrapped):
    `05: API contract for <slug> via ao-api-forge`. Then the handoff block
    ([handoff](./references/shared/handoff.md)): *What I did* (verdict, scenario, rules file
    bootstrapped or not, codegen result), *Review* (`openapi.yaml`, `api-sync-report.md`,
    `events.md`), *Run next*: on `PASS` / `PASS (with deferrals)` -> `/clear`, then
    `/sdlc:break-tasks <slug>`; on `FAIL` -> the fix-the-source command the report names
    (`/ao-prd <slug>`, `/ao-architecture <slug>`, `/sdlc:complete-sequence-diagrams <slug>`,
    `/sdlc:generate-data-model <slug>`), then `/ao-api-forge <slug> --reconcile`.

## What differs from sdlc:api-forge

| Step | sdlc:api-forge | ao-api-forge |
|------|----------------|--------------|
| Gate | `PRD.md` | `PRD.md` or `PRD.ao-prd.md` (pick when both); SAD and data-model variants picked the same way |
| Inputs | PRD + data-model + sad §6 + adr | + ao-prd §5.1 error catalogue and §10 RBAC; repo contract, goose migrations, `httpapi`, codegen configs |
| Contract scope | one feature contract | a **delta** for `services/core/api/openapi.yaml`: one tag per context, paths `/<context>/...` |
| Versioning | `/api/v1/...` | none in the URL (single deployable, spec-first, repo ADR 0003) |
| Errors | `{code, message, details?}` | RFC 9457 `application/problem+json`, `type` = `urn:problem:<context>.<error_name>`, 422 with `errors[].pointer`; codes listed per status in `x-problem-types` |
| Status map | 400 validation, 409 conflict | validation 422, not_found 404, invariant / conflict 409, authorization 403, authentication 401, unavailable 503 |
| Pagination | `after/before/limit`, `{items, has_next, has_prev, next_cursor}` | repo keyset: `limit` + opaque `cursor`, `{items, next_cursor}` over `(created_at, id)` |
| Auth | `BearerAuth` JWT | `SessionCookie` (`apiKey` in cookie) after Google sign-in; 401 / 403 on every protected op |
| Field origin | `varchar(N)`, `CHECK`, ENUM | + `text` + `CHECK char_length` -> min/maxLength, `CHECK IN` -> named enum, `bigint` minor units -> int64 + `Currency`, `date` vs `date-time` |
| Async | `events.md` `module.action.vN` envelope | River job contract: ids only, unique key, retries, trace context |
| Ban-list | inline schemas, PII, `nullable: true` | + HTTP verbs / status codes in §6 messages, missing `operationId`, multi-type unions |
| Drift checklist | 5 points | 9: + §5.1 codes as problem types, cursor params on lists, tag = context + path prefix, delta merges and generates |
| Codegen | suggest `spectral lint` | scratch `oapi-codegen` (version from `tools/go.mod`) + `go build` + scratch orval |
| Rules file | course baseline | repo baseline; never overwrites an `sdlc:api-forge` one silently |
| Commit | `api: <slug> contract` | `05: API contract for <slug> via ao-api-forge` |
| Output | `contracts/` | `contracts.ao-api-forge/` next to contracts from another skill |
| Other forms | cli.md, public-api.md, gRPC | out of scope (the repo has none) - use `sdlc:api-forge` |

## Definition of Done

- Contract at the collision-rule path: OpenAPI 3.1.0, every operation with one context tag, a
  `/<context>/` path, an `operationId`, examples, `$ref`-only schemas, `x-problem-types` on every
  operation with a 4xx/5xx; global `SessionCookie` security with explicit `security: []` on public ops.
- Scratch codegen generated and built; scratch orval ran (or was reported as skipped with reason).
- `api-sync-report.md` with `**Verdict:**` first, field-origins table, the 9-point checklist,
  `unresolved_origins` (empty in A), `Deferrals` (or `none`), merge notes for the repo contract.
- Verdict `PASS` or `PASS (with deferrals)`; a `FAIL` report is a valid artifact but the stage is not done.
- `events.md` present iff a job is enqueued; `.claude/rules/openapi.md` exists and the report says
  whether it was bootstrapped.
- One commit with the message above; the handoff block printed.

## Anti-patterns

- Editing `services/core/api/openapi.yaml` or running a context's own `oapi-codegen.yaml` on the
  delta: its `output:` wins over `-o` and overwrites the real `*.gen.go`. Use the scratch config.
- An inline schema, a schema duplicated under two names, or a component whose shape differs from the
  same name in the repo contract.
- A §5.1 code missing from `x-problem-types`, or a problem type not in §5.1 without a report note.
- Offset pagination, `has_prev`, or a cursor that is not opaque.
- `type: [integer, string]` and other multi-type unions (oapi-codegen v2 fails on them);
  `nullable: true`; `additionalProperties: true` on responses.
- Real names, phones, emails or IBANs in examples.
- Copying an HTTP verb or a status code from a §6 message as if the sequence decided it: report
  it as a sequence finding, derive the contract from the domain message.
- Writing `PASS` over an open finding, or ending a FAIL in the chat only.
- Overwriting contracts or a rules file written by another skill.
